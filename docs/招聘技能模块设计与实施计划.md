# AgentHR 招聘技能模块设计与实施计划

## 1. 产品判断

AgentHR 应借鉴 `workflow-use` 的核心思路：首次由 Agent 理解目标并完成任务；经过验证的高频流程，再沉淀为可重复执行、可审计、可持续优化的招聘技能。

这里的“技能”不是一段不可理解的自动化脚本，而是一份招聘人员能读懂的业务协议：它明确输入参数、执行步骤、每步验证、成功标准、权限边界和失败策略。用户能看见它、启停它、运行它，也能通过与 Agent 对话提出修改意见。

## 2. 目标

- 降低重复招聘操作的对话成本。
- 把成功经验从一次性对话转成团队可见资产。
- 保留 Agent 对复杂页面和异常情况的适应能力。
- 让每次技能运行都关联岗位、任务、版本和审计记录。
- 让技能优化以人能审核的版本差异呈现。

## 3. 非目标与安全边界

当前阶段不允许模型生成或持久化以下内容：

- CSS/XPath selector。
- 任意 JavaScript 或页面注入脚本。
- 任意 CDP 命令。
- 绕过平台权限、验证码或风控的动作。
- 未经确认的候选人外部沟通、附件下载或不可逆操作。

原因不是限制 Agent 的理解能力，而是把不稳定、不可审核、可能越权的页面控制细节留在受控适配器中。技能只声明“要完成什么、如何验证、允许做什么”，底层能力负责“如何安全地执行”。

## 4. 产品形态

侧边栏新增“招聘技能”模块。每个技能展示：

- 名称、描述、适用平台和当前版本。
- 执行方式：Agent 引导或确定性工作流。
- 风险级别和权限边界。
- 可编辑的运行参数。
- 语义化执行步骤及逐步验证。
- 成功标准、失败回退策略和运行统计。
- 启用/停用、运行技能、与 Agent 优化三个入口。

技能库按适用范围分为三类：

- 通用技能：不依赖单一招聘平台，可用于 BOSS 直聘和猎聘。
- BOSS 直聘：只使用 BOSS 会话和平台适配能力。
- 猎聘：只使用猎聘会话和平台适配能力。

用户点击“与 Agent 优化”后，系统把当前技能完整上下文带入对话。Agent 先了解用户要改善的问题，再输出可审核的版本差异；后续版本开放后，用户确认才能发布新版本。

## 5. 技能生命周期

```text
一次性 Agent 任务
  → 执行成功并收集证据
  → 识别为高频、稳定流程
  → 生成技能草稿
  → 人工审核权限与成功标准
  → 发布版本
  → 重复运行
  → 失败时保留断点并回退 Agent
  → 修订、验证、发布新版本
```

技能状态：

- `draft`：草稿，不能运行。
- `enabled`：已启用，可以运行。
- `disabled`：人工停用。
- `needs_repair`：连续失败或平台变化，需要 Agent 诊断。

## 6. 执行模型

### Agent 引导

首版技能将结构化定义转换为受审计的招聘任务，再交给 Agent 执行。它适合页面变化较多、需要阅读语义和处理异常的流程。

### 确定性工作流

后续仅把已经多次验证且底层适配器能力稳定的步骤升级为确定性工作流。任何语义目标、页面前置条件或结果校验失败，都立即停止确定性动作，保存执行断点并回退 Agent。

### 失败回退

失败不是无限重试。系统需要保存：失败步骤、结构化错误、页面安全快照、已完成步骤和当前技能版本。Agent 基于这些证据诊断；涉及权限扩大或外部动作时，必须重新请求用户确认。

## 7. 数据模型

本地 SQLite 技能闭环包含五类数据：

- `recruitment_skills`：技能元数据、状态、活跃版本和运行统计。
- `recruitment_skill_versions`：不可变的版本化定义和变更摘要。
- `recruitment_skill_runs`：一次运行关联的技能版本、招聘任务、参数和结果。
- `recruitment_skill_sources`：草稿来自哪些成功任务、对话结论和 DSH 浏览器操作记录。
- `recruitment_skill_run_steps`：步骤级状态、完成证据、失败代码和恢复断点。

技能定义采用结构化 JSON，包含：

- `taskType`
- `parameters`
- `steps[]`：标题、业务描述、验证条件
- `permissions[]`
- `successCriteria[]`
- `failureStrategy`

## 8. 首版内置技能

1. 通用：读取当前简历并补全人才资料。
2. 通用：按岗位逐项分析当前简历。
3. BOSS 直聘：推荐页读取并保存候选人。
4. 猎聘：搜索并保存候选人。

四者均默认禁止自动联系候选人，涉及资料写入时仅写入 AgentHR 本地人才库或分析草稿。

### 阶段三：成功流程自动沉淀

- [x] 从历史和新完成的成功任务中提取候选技能草稿；任务条目同时承载对话结论和 DSH 操作证据。
- [x] 以平台、任务类型和规范化操作序列生成指纹，并按相似度合并流程，避免技能重复膨胀。

- [ ] 沙箱验证修订版本，通过后再请求人工发布。
- [x] 同一技能连续 3 次运行失败后自动标记 `needs_repair`，成功一次即清零。

## 10. 与 DSH Skill Manager 的边界与接入建议

当前 DSH 已内置 `@deepseek-ai/dsh-skill` 注册表和 `@deepseek-ai/dsh-skill-filesystem` 文件提供器。后者会发现并监听项目或用户技能目录中的 `SKILL.md`，因此 AgentHR 不需要再实现一套技能加载器。

但不建议把每个自动提取结果立即写进 DSH：业务草稿尚未验证权限、步骤和成功标准，直接进入模型可调用目录会把噪声和错误一起放大。建议采用两层模型：

1. AgentHR 是业务技能的真源，负责提取、证据归并、版本、运行、断点、失败统计和人工审核。
2. DSH Skill Manager 是发布目标，负责发现、加载和在对话中调用已经审核的 `SKILL.md`。
3. `draft` 只保存在 AgentHR；审核通过并达到稳定性门槛后，导出到项目级 `.agents/skills/agenthr-<key>/SKILL.md`。
4. 导出文件只包含业务参数、语义步骤、验证、权限和 AgentHR 工具调用约定，不包含 selector、任意脚本或任意 CDP 命令。
5. AgentHR 保存发布路径和技能版本；技能被标记 `needs_repair` 时撤销模型可调用标志或停止更新发布版本，修复验证后再发布。

结论：可以接入 DSH 的技能管理，并且它很适合作为“发布层”；自动提取、去重、运行证据和修复状态仍应留在 AgentHR 业务层。下一步应增加明确的“审核并发布到 DSH / 撤回发布”动作，而不是草稿自动直写。

## 11. 首版验收标准

- 应用启动后能看到 4 个内置技能。
- 技能定义在重启后保持不变。
- 用户能查看完整业务语义，不暴露或保存页面 selector/脚本/CDP。
- 用户能启停技能；并发修改会被版本时间戳拒绝。
- 运行技能前验证当前岗位、技能状态和声明参数。
- 每次运行创建招聘任务、技能运行记录和审计事件。
- “与 Agent 优化”提供完整技能上下文，并明确当前只生成待审核草案。
